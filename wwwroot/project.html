Boost Searcher 中的搜索、BM25F 与编辑距离模糊召回

本文只解释项目当前已经实现的检索逻辑：一条查询如何进入索引、BM25F 如何排序、错别字如何被模糊召回，以及现有实现还缺少什么、下一步可以怎样优化。

说明依据：当前 Index、Searcher 实现和项目 README。文中“优化方向”均为尚未实现的后续建议。

一、项目中的搜索流程

Boost Searcher 是一个本地 Markdown 文档搜索服务。它不会在每次查询时逐篇扫描所有文档，而是先在启动时把语料构造成内存索引，再在查询时按词直接取得候选文档。这样做的核心目的，是把“在所有文档中找词”的工作尽量前置到索引构建阶段。

1. 离线解析与索引构建

parser 会读取 data/raw/md/ 下的 Markdown 文件，抽取标题、正文和相对路径，并写入 data/raw.txt。服务启动后，Index 会读取该语料并构建两类索引：

  • 正排索引：按 doc_id 保存标题、正文和路径。搜索阶段已经得到文档编号时，可以从这里取回展示所需的内容。
  • 倒排索引：保存 词 → 文档列表 的映射。每个倒排项还分别记录这个词在标题和正文中的出现次数，供后续 BM25F 计算。

标题和正文都会通过 cppjieba 分词。项目同时记录每个字段的分词长度，以及全库标题、正文的平均分词长度。这些长度统计不是为了展示，而是 BM25F 做长度归一化时的输入。

2. 一次查询如何执行

  1. 查询文本先分词，并过滤“的”“了”“和”等停用词；ASCII 字符会统一转为小写。
  2. 每个查询词先查倒排索引。若存在精确倒排链，就按精确命中的权重参与评分。
  3. 若某个词没有精确倒排链，才会进入编辑距离模糊召回。模糊候选会降权，避免压过精确结果。
  4. 同一篇文档命中多个查询词时，分数累加。候选合并后，短语命中只增加小额修正，主排序仍由 BM25F 决定。
  5. 结果按分数从高到低排序，最终返回标题、摘要、路径和命中词等 JSON 字段。
这条流程的设计重点是“先缩小候选集合，再做精细排序”。倒排索引负责召回候选，BM25F 负责判断候选之间谁更相关，模糊搜索只在精确召回失败时补充结果。

二、BM25F 相关性排序

BM25（Best Matching 25）是信息检索中经典的统计排序算法，用来计算查询文本与目标文档的相关性。它比简单的关键词匹配或固定词频累加更符合直觉：一个词重复出现并不应该无限加分；特别长的文档不应该仅因为词多就天然占优；罕见术语通常也比常见词更能表达主题。

1. BM25 解决什么问题

  • 词频饱和：词出现 1 次和 2 次通常有明显差别，但出现 10 次和 20 次不应让相关性翻倍。BM25 让词频收益逐渐变小，防止正文反复堆词刷分。
  • 文档长度归一化：长正文包含更多词，更容易随机命中查询词。BM25 使用当前文档长度和全库平均长度比较，对过长字段适当降分。
  • 逆文档频率：专业词出现在少数文档中时，通常比高频常见词更能区分主题，因此应该得到更高权重。

2. BM25 的基本公式

对查询 Q 中的每个词 t，BM25 计算它在文档 D 中的贡献，再把所有词的贡献相加：

Score(D,Q) = ∑t∈Q IDF(t)· f(t,D) (k1+1) f(t,D) +k1(1−b +b·|D|avgdl)
  • f(t, D)：词 t 在文档 D 中的出现次数，也就是词频。
  • |D| / avgdl：当前文档长度与平均文档长度的比值，用来做长度归一化。
  • k1：控制词频饱和的速度。值越小，词频越早进入“重复再多也加分不多”的状态。
  • b：控制长度归一化的强度，取值范围通常在 [0, 1]。

项目使用的 IDF 变体如下。额外的 log(1 + ...) 平滑可以避免高频词在小语料或极端语料中得到负分：

IDF(t)= log(1+ N−df(t)+0.5 df(t)+0.5 )

其中 N 是文档总数，df(t) 是包含词 t 的文档数。

3. 项目中的 BM25F：标题和正文分开计算

本项目并非把标题和正文混成一段文本，而是采用轻量的 BM25F 思路：标题、正文各算一次 BM25，再按字段权重合并。

Score(t,doc)= 3·BM25(title) +BM25(content)

当前参数：k1 = 1.5，b = 0.75，标题权重为 3，正文权重为 1。

这样做的原因是标题通常更集中地概括文章主题。假设一篇文章标题直接包含查询词，另一篇文章只是在很长的正文中重复该词，标题命中的文章通常更应该排在前面。项目测试也专门覆盖了这一点。

4. BM25F 的现有不足与优化方向

当前 k1、b、标题权重和短语加成都写成固定常量。它们对当前语料可以工作，但还没有通过真实查询集证明是最优组合。BM25F 本身也属于字面匹配算法，不能理解同义表达或上下文语义。

后续可以先收集“查询 → 期望文档”的标注样本，以 NDCG、MRR、Hit@K 等指标衡量排序质量；再比较不同 k1、b 和字段权重组合。若需要更强的语义理解，可以在 BM25F 召回后增加同义词扩展或语义重排，但这些都属于后续能力，不是当前实现。

三、编辑距离模糊召回

BM25F 的前提是查询词已经命中倒排索引。但用户可能输入错别字，例如把“协议”输入为“协义”。如果只做精确匹配，这个词会完全没有结果。项目因此加入了编辑距离模糊召回，用来补充精确查询找不到的词。

1. 当前策略：精确优先，模糊降权

编辑距离表示把一个词变成另一个词最少需要多少次插入、删除或替换。项目的模糊策略并不会对每个查询词都执行，而是遵循下面的限制：

  • 先查精确倒排链。精确命中时，直接使用精确结果，不进入模糊召回。
  • 单字查询不做模糊匹配，因为单字容错很容易召回大量噪声。
  • 查询词长度为 2 到 4 个字符时，允许的最大编辑距离是 1。
  • 查询词长度为 5 个字符及以上时，允许的最大编辑距离是 2。
  • 候选词按编辑距离和词长排序，最多保留 5 个候选。
  • 模糊候选进入 BM25F 时统一按 60% 权重降分，精确命中仍是 100%。

这种保守设计的目的不是让模糊匹配“尽可能多找”，而是让错别字有机会召回相关内容，同时避免相近但不相关的词排到精确结果前面。

2. 当前不足

  • 错词查询会扫描整个词典：当前实现遍历倒排词典，逐个计算编辑距离。代码已经利用词长差和动态规划行最小值做剪枝，但总体成本仍会随词典规模增长。
  • 候选评分较粗：距离为 1 和距离为 2 的候选，目前都会使用统一的 60% 权重，没有进一步区分可信度。
  • 只能处理字面接近：编辑距离无法识别拼音、同音字、同义词或语义相近表达。

3. 优化方向

当词典继续增大时，可以先用 BK-tree 或 trigram 索引缩小候选集合，再对小候选集计算精确编辑距离。README 也列出了 BK-tree、trigram、拼音和同音召回作为后续方向。评分上可以让距离更小的候选获得更高权重，而不是所有模糊候选都固定为 60%。

四、当前不足与优化顺序

当前版本适合本地 Markdown 语料的可验证原型：可以完成中文分词、倒排召回、BM25F 排序和基础错别字容错。继续演进时，建议先通过数据证明问题，再增加算法复杂度。

  1. 先补相关性评估。现有测试已经覆盖精确搜索、模糊搜索、BM25 标题优先、并发稳定性、QPS 和平均延迟，但还没有 NDCG、MRR、Hit@K、P95/P99 或 HTTP 端到端压测。先建立查询集和指标，才能判断调参是否真的有效。
  2. 再优化模糊候选。当错词查询的词典扫描成为瓶颈时，引入 BK-tree 或 trigram 索引；然后根据编辑距离、词长和候选质量设计更细的降权策略。
  3. 最后演进索引生命周期。当前 HTTP 服务启动时一次性构建内存索引，不支持运行时增量更新。文档频繁变化或语料扩大后，可以考虑增量更新和持久化索引，减少全量重建成本。
总结来说，倒排索引解决“从哪里找”，BM25F 解决“谁更相关”，编辑距离模糊召回解决“输入错了还能不能找到”。三者组合构成当前项目的基础检索能力；后续优化的关键，是用质量指标和真实数据驱动每一步演进。
