# 新增项目关键价值介绍页面与接口

## 目标

为 Boost Searcher 提供一个可从首页进入的纯静态核心技术原理页，帮助面试官在短时间内理解项目的检索链路、关键算法和设计取舍。

## 已知信息

* 用户要求新建前端文档和接口，专门介绍项目关键价值；已进一步收紧为仅展示核心技术原理，页面面向面试官，并明确要求全部内容放在 HTML 中、不改动 C++ 代码。
* 用户要求重新设计页面，重点讲搜索、BM25 和编辑距离模糊召回的当前设计、现有不足及后续优化方向。
* 用户明确要求页面使用普通技术文档式文字，不使用卡片、流程图或装饰性视觉模块；BM25 讲解密度参考用户提供的经典定义、直觉、公式、参数和工程总结结构。
* 静态资源目录是 `wwwroot/`；`http_server` 通过 `set_base_dir` 自动提供该目录中的页面。
* 首页 `wwwroot/index.html` 已有深浅色主题，并使用 `boost-searcher-theme` 保存偏好。
* 文章页 `wwwroot/blog.html` 也使用同一主题键，并通过 `fetch` 调用后端接口。
* 后端 HTTP 接口定义在 `engine/src/http_server.cc`：`/s` 返回 JSON 搜索结果，`/doc` 有参数校验、状态码和中文错误消息。
* 已实现的、可据实介绍的能力包括本地 Markdown 解析、中文分词、BM25F 相关性排序、保守模糊召回、文档阅读，以及 `data/raw/md/` 范围的路径保护。
* 现有 CMake 将核心能力编入 `search_engine` 静态库；测试通过 CTest 运行 `searcher_tests`。

## 临时假设

* 新页面使用项目现有的原生 HTML、CSS 和 JavaScript，不引入前端框架或第三方依赖。
* 页面直接写入经过源码核验的技术说明，不发起额外 HTTP 请求。
* 页面内容只描述当前代码已有的技术原理和取舍，不宣传未实现的 AI、增量索引或端到端性能指标。

## 开放问题

* 无。用户已确认页面主要面向技术学习者。
* 用户已确认按“面向面试官、仅展示核心技术原理”的范围开始实现。

## 需求（持续完善）

* 新增一个可直接访问的项目介绍页面，并从首页提供入口。
* 不新增或修改 C++ HTTP 接口、核心库、CMake 配置和测试代码。
* 页面复用现有深浅色主题行为和视觉基调。
* 页面面向面试官：每项技术原理应包含“解决什么问题、如何实现、为何这样取舍”三个简短说明，避免营销性表述。
* 页面改为连续技术文档：搜索系统设计、BM25F 相关性排序、编辑距离模糊召回、当前不足与优化方向四个章节；使用标题、段落、列表和公式块组织内容。
* 页面不使用卡片、网格、流程图、指标墙或装饰性视觉模块；只保留基础排版、目录、返回首页链接和主题切换。
* 技术内容仅基于当前实现，覆盖 Markdown 到统一语料和正倒排索引的数据流、中文分词与 BM25F 相关性排序、以及保守的编辑距离模糊召回。
* BM25F 章节必须说明当前标题权重 3、正文权重 1、`k1=1.5`、`b=0.75`，以及词频饱和、IDF、长度归一化各自解决的问题。
* 模糊召回章节必须说明“精确优先”、单字禁用、2 至 4 字允许距离 1、5 字及以上允许距离 2、候选上限 5 和 60% 降权。
* 优化建议必须区分已实现事实与未来方案；至少覆盖相关性评估与参数调优、BK-tree 或 trigram 候选索引，以及增量索引或持久化索引方向。
* 不在页面中展示文档阅读安全边界、主题交互或其他非检索核心技术。
* 以现有静态资源服务验证页面和首页导航的真实访问行为，并检查浏览器控制台无错误。

## 验收标准（持续完善）

* [ ] 首页能打开项目介绍页面。
* [ ] 介绍页面在不请求新增接口的情况下正确展示检索链路和三个核心技术点。
* [ ] 页面中的每项技术原理均能在当前实现或 README 中找到依据。
* [ ] 每项技术原理都能用面试交流中容易理解的语言说明问题、实现和取舍。
* [ ] 三个核心章节及总结章节均使用普通文字清楚说明当前设计、已知不足和可落地优化方向，且优化项不会被表述为已实现功能。
* [ ] BM25F 章节包含当前实现对应的得分公式、IDF 公式、符号与参数解释，以及工程局限说明。
* [ ] 页面在浅色和深色主题下均可阅读，主题选择与现有页面保持一致。
* [ ] 现有 CTest 通过，证明静态页面改动未影响搜索功能。
* [ ] 浏览器能打开页面、从首页完成跳转，且控制台无错误。

## 技术方案（候选）

### 方案 A：独立纯静态介绍页（已选择）

新增独立 HTML 页面，把经过源码核验的说明直接写入页面。页面以一条检索链路串联技术点，并用技术卡片补充算法原理与取舍。

* 优势：没有额外接口、异步加载或 C++ 改动；适合面试现场稳定展示。
* 劣势：技术说明更新时需要直接修改 HTML。

### 方案 B：独立介绍页加 JSON 接口（未选择）

页面用 `fetch` 请求固定 JSON 接口，后端维护技术说明内容。

* 优势：页面和外部调用者可以共享同一内容源。
* 劣势：需要修改 C++ 服务和构建测试，超出当前纯静态范围。

## 关键风险点

* 内容准确性：不能把仓库历史描述、未来设想或框架默认能力当成现成功能。
* 表述边界：BM25F、模糊召回和索引结构需解释到能够说明设计决策的深度，避免把实现细节堆成源码注释。
* 链接可用性：首页入口和返回首页链接必须使用静态资源服务下的绝对路径。

## 扩展评估

* 后续可在页面中增加版本、索引文档数或性能指标；这些动态信息需要定义刷新时机和可信来源，本次不纳入。
* 后续可为每个技术点链接到源码或设计文档；本次先保持单页、固定且可验证的介绍，避免引入链接维护成本。
* 本次页面不依赖新增接口或网络请求，不会影响现有搜索和阅读流程。

## 决策（轻量 ADR）

**背景**：项目已有搜索页、文章页和同源 HTTP 接口，但缺少面向面试官的核心技术原理总览。

**决策**：采用独立纯静态技术原理页。页面先说明检索数据流，再以技术卡片解释正倒排索引、中文分词与 BM25F、以及保守模糊召回。首页增加到页面的导航入口。

**影响**：页面展示稳定、无额外后端改动；固定内容不反映运行时指标，日后如需动态指标应另行设计接口契约。

## 范围外

* 不新增搜索功能、索引更新机制或 AI 摘要。
* 不改动现有 `/s`、`/doc` 接口语义，也不新增接口。
* 不增加新的前端构建工具或外部运行时依赖。
* 不展示或导出运行时索引规模、查询性能等动态指标。
* 不添加产品价值宣传、功能清单或非检索核心技术说明。

## 技术笔记

* 已查看的现有模式：`wwwroot/index.html`（首页和主题）、`wwwroot/blog.html`（页面级 `fetch` 与主题复用）、`engine/src/http_server.cc`（路由、响应与错误处理）、`engine/CMakeLists.txt`（可测试核心库）、`tests/searcher_tests.cc`（手写断言测试）。
* 页面数据流：经过源码核验的静态技术说明 -> `/project.html` 直接渲染；首页仅提供导航入口。
* 页面路径为 `/project.html`。
