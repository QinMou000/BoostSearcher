# 为工具 Python 脚本添加独立日志

## 目标

为当前 `tools/` 中的 Python 脚本补充可追踪的运行日志，便于定位同步过程中的成功、跳过和失败情况；不同脚本不得共用同一个日志文件。

## 已知信息

* 用户要求为当前工具中的 Python 脚本添加日志，格式与现有项目日志大致一致。
* 用户明确要求不同脚本使用不同的日志文件。
* 当前 `tools/` 目录包含 `sync_gitee_posts.py` 和包标记文件 `__init__.py`；其中只有前者是可执行 Python 脚本。
* `sync_gitee_posts.py` 当前仅在入口异常分支向标准错误输出错误信息，尚未配置 `logging`。
* C++ 运行时日志的字段顺序为 `[级别] [YYYY-MM-DD HH:MM:SS] [消息] [文件 : 行号]`，根目录的 `http.log` 由 HTTP 服务使用。
* `.gitignore` 已忽略 `*.log`，工具运行产生的日志不会成为待提交文件。
* 同步函数把终端输出抽象为 `print_line` 参数，单元测试以列表收集输出；入口层可在不改变同步核心接口的前提下同时写入终端和日志。
* 现有离线单元测试以 `unittest` 运行，且通过注入 `FakeFetcher` 避免访问真实 Gitee。

## 需求

* `sync_gitee_posts.py` 将日志写入仓库根目录的 `sync_gitee_posts.log`，与 `http.log` 和未来其他脚本的日志文件隔离。
* 新增的日志行使用 `[级别] [YYYY-MM-DD HH:MM:SS] [消息] [文件 : 行号]` 格式，时间使用本地时区。
* 正常命令行运行时，启动信息、同步过程中已有的汇总/预览/新增/更新/跳过/失败信息及最终结果必须写入日志；终端输出保持不变。
* `SyncError` 导致的入口失败必须同时保留标准错误输出，并以 `ERROR` 级别写入日志。
* 只使用 Python 标准库；不改变同步规则、网络请求、文件发布和退出码。

## 验收标准

* [ ] 默认日志文件为 `<仓库根目录>/sync_gitee_posts.log`，不是 `http.log`，并可由脚本名称稳定推导。
* [ ] 日志格式包含 `INFO` 或 `ERROR`、本地时间、消息、Python 文件名和行号。
* [ ] 同一次运行不会因重复初始化而重复写入同一条日志。
* [ ] 成功与失败运行均会写入对应脚本的独立日志文件。
* [ ] 现有命令行行为和退出码保持可用。
* [ ] 离线自动化测试覆盖独立日志文件选择、格式、成功事件、错误事件及重复初始化。

## 完成定义

* 完成代码和自动化验证。
* 遵循仓库现有格式化和测试方式。
* 记录无法覆盖的风险及补测计划。

## 范围外

* 不改动同步业务规则、远程接口或文章数据。
* 不聚合多个脚本的日志，也不引入集中式日志服务。

## 技术说明

* 已分析的既有模式：
  * `engine/src/log.cpp` 和 `tests/log_tests.cc`：固定字段顺序和本地时间格式，测试使用正则完整校验一行日志。
  * `tools/sync_gitee_posts.py` 的 `sync_posts(..., print_line=...)`：核心业务和输出通道解耦，可在 `main` 注入“终端输出加文件日志”函数。
  * `tests/test_sync_gitee_posts.py` 的 `FakeFetcher` 与临时目录：全部日志测试均可离线运行，且不污染仓库真实数据。
* 依赖与集成点：`main` 解析参数后初始化日志器；日志器向文件追加 UTF-8 文本；`sync_posts` 通过注入输出函数产生运行事件；`SyncError` 经入口转换为标准错误输出和非零退出码。
* 方案：使用标准库 `logging.FileHandler`，日志文件名由当前脚本文件名推导；记录器关闭向根记录器传播，并对同一目标文件复用处理器，避免重复行。
* 优势：与项目格式一致、无需依赖、不会改动核心同步接口、未来新脚本自然拥有独立日志。
* 风险：日志目录不可写时可能掩盖业务同步。实现中应让日志初始化错误清晰暴露且不误报同步成功；日志文件持续增长暂不轮转，后续若运行频率提高可独立引入轮转策略。
